# Аудит энергопотребления интерфейса Astra

> Результат прогона по `docs/TASK_ENERGY_OPT.md` (2026-07-09). Код НЕ менялся —
> это исследование + пошаговое задание для дешёвых моделей (Sonnet/Haiku).
> Анализировался веб-бандл (Vite + Svelte 5); приложение — тот же бандл в
> Capacitor, немногие отличия WebView — в разделе D.
>
> Главное ограничение выдержано: **минимум потерь красоты**. Полная графика
> остаётся дефолтом; всё тяжёлое гасится ступенчато через уже существующий
> `settings.batterySaver` → `data-saver='on'` на `<html>`.

## Резюме (одним абзацем)

Постоянный расход в форграунде дают четыре вещи: canvas-блёстки Starfield
(rAF 30 к/с на весь экран, всегда), аврора-дрейф (композиция fixed-слоя
~160%×160% вьюпорта, infinite), `backdrop-filter: blur(12px)` на шапке и
таб-баре (пересчёт размытия на каждом кадре прокрутки ленты — а прокрутка
ленты и есть главный жест) и, при выбранном стиле знаков shimmer/rainbow,
SMIL-анимации градиентов, которые перерисовывают SVG колеса непрерывно.
Существующий saver-режим гасит первые три, но имеет **две дыры**: SMIL-анимации
CSS-правилом `animation-duration` не останавливаются, и глоу-фильтр
зодиакального кольца (`.ring.zodiac`) в списке `filter: none` отсутствует.
Остальное — мелочь (короткие one-shot анимации, opacity-пульсы крошечных
элементов, статичные text-shadow) или осознанные CPU-пики по жесту
(WASM-скраб колеса). Фонового расхода нет: rAF и таймеры в свёрнутом
приложении/вкладке стоят (см. D).

## B. Пошаговое задание для дешёвых моделей

Правила для исполнителя: один шаг = один заход одной модели; партии по 3–4
правки, коммит и пуш после КАЖДОЙ партии; новых зависимостей не добавлять;
движок расчётов и авторские тексты не трогать. Проверка каждого шага:
`npm run build` + `npx svelte-check` в `app/` — 0 ошибок. Все шаги — «оба»
(сайт и приложение), код общий; исключения помечены.

### Партия 1 — закрыть дыры saver-режима

**Шаг Б-1. Saver останавливает переливы знаков (SMIL).** Файл `app/src/App.svelte`.
CSS не умеет останавливать `<animateTransform>`, поэтому подменяем стиль на
статичный на время saver — на уровне пропа, по существующему паттерну
`data-saver`.
- Было: флаг saver считается только внутри `$effect` (`App.svelte:344-350`);
  в `DayScreen` (строка ~396) и `ChartsSheet` (строка ~498) передаётся
  `signStyle={settings.signStyle}`.
- Стало: вынести вычисление в реактивную переменную и завести эффективный стиль:
  ```ts
  const saverActive = $derived(
    (settings.batterySaver ?? 'auto') === 'on'
    || ((settings.batterySaver ?? 'auto') === 'auto' && lowBattery));
  const effSignStyle = $derived(
    saverActive && (settings.signStyle === 'shimmer' || settings.signStyle === 'rainbow')
      ? 'gold' : settings.signStyle);
  ```
  Существующий `$effect`, ставящий `data-saver`, переписать на `saverActive`
  (поведение не меняется). В оба места передавать `signStyle={effSignStyle}`.
- Приёмка: включить в Настройках стиль «переливы», включить «Экономию» —
  значки знаков становятся золотыми и статичными; выключить — переливы
  возвращаются сразу. Без saver ничего не изменилось.

**Шаг Б-2. Saver гасит глоу зодиакального кольца.** Файл `app/src/app.css`.
- Было (`app.css:269-273`): список `filter: none !important` без `.ring.zodiac`.
- Стало: добавить строку `:root[data-saver='on'] .ring.zodiac,` в тот же
  список (Svelte scoped-классы сохраняют исходное имя — глобальный селектор
  матчится, как уже матчатся `.selline`/`.signicon` из того же компонента).
- Приёмка: в saver у колеса нет `drop-shadow` ни на одном элементе
  (проверить в DevTools → Rendering → Paint flashing или просто computed
  style кольца); без saver свечение кольца на месте.

**Шаг Б-3. Starfield: адаптив к слабому железу.** Файл
`app/src/ui/Starfield.svelte`. Красоту у сильных телефонов не трогаем; у
слабых — меньше частиц и кадров (глазом почти неотличимо: пыль остаётся,
плотность чуть ниже).
- Было: константы `COUNT = 81`, `MIN_FRAME_MS = 31` (`Starfield.svelte:9-11`).
- Стало:
  ```ts
  const weak = (navigator.hardwareConcurrency ?? 8) <= 4;
  const COUNT = weak ? 54 : 81;
  const MIN_FRAME_MS = weak ? 42 : 31;   // слабое железо: ~24 fps вместо ~30
  ```
- Приёмка: на десктопе (ядер > 4) поведение байт-в-байт прежнее; сборка и
  svelte-check чистые. Визуально при `weak` блёстки есть, просто реже.

### Партия 2 — сузить без потери

**Шаг Б-4. Полл бейджа карт: реже и не в saver.** Файл `app/src/App.svelte`
(строка ~218).
- Было: `setInterval(() => void refreshClientCharts(), 120000)`.
- Стало: интервал `300000` (5 мин) и пропуск тика в saver:
  ```ts
  onMount(() => {
    const t = setInterval(() => {
      if (document.documentElement.dataset.saver === 'on') return; // экономия: радио не будим
      void refreshClientCharts();
    }, 300000);
    return () => clearInterval(t);
  });
  ```
  Обновление при возврате в приложение уже есть (`appStateChange`,
  `App.svelte:224`) — свежесть бейджа при открытии не страдает.
- Приёмка: бейдж по-прежнему обновляется при старте и возврате в приложение;
  в DevTools → Network за 5 минут не больше одного запроса `client_charts`
  (и ни одного при включённой «Экономии»).

**Шаг Б-5. Scroll-нить шторки: убрать layout-рид из горячего пути.** Файл
`app/src/lib/sheet.ts` (`attachThread`, строки ~81-100).
- Было: `measure()` на каждое scroll-событие делает
  `node.getBoundingClientRect()` и пишет `el.style.top/height`.
- Стало: разнести на два измерения. Геометрию коробки (`top`/`height`) мерить
  только в `place()` — вызывать при attach, `resize`, `transitionend` и из
  ResizeObserver. Прогресс (`fill`/`carrier` transform) — в `onScroll`,
  тротленном через rAF:
  ```ts
  let ticking = false;
  const onScroll = () => {
    if (ticking) return;
    ticking = true;
    requestAnimationFrame(() => { ticking = false; progress(); });
  };
  ```
  где `progress()` — прежний расчёт `p` + два `style.transform`, БЕЗ
  `getBoundingClientRect`. Существующие подписки (scroll/resize/
  transitionend/RO) сохранить, только развести по двум функциям;
  `remeasureThreads()` должен звать обе.
- Приёмка: нить шторки ведёт себя как раньше (появляется у верхней шторки,
  ползёт при скролле, подгоняется после выезда); в Performance-профиле
  прокрутки шторки нет Forced reflow от `sheet.ts`.

**Шаг Б-6 (опционально, на вкус владелицы). «Рассвет»: гало только у заметных
блёсток.** Файл `app/src/ui/Starfield.svelte` (строки ~82-85). Сейчас на
светлой теме тёплое гало рисуется у ВСЕХ 81 частиц (лишний draw-вызов на
частицу на кадр). Рисовать гало только при `p.r > 1.1` — мелкие пылинки его
всё равно не показывают глазу.
- Приёмка: на «Рассвете» крупные блёстки по-прежнему тёплые с ореолом,
  картинка не «холодеет»; показать владелице до/после, при сомнении — откатить.

### Партия 3 — аварийный минимум (ТОЛЬКО после «да» владелицы, см. C)

**Шаг Б-7. Порог критического заряда в watcher'е.** Файл `app/src/lib/battery.ts`.
Расширить колбэк до `(low: boolean, critical: boolean)`: `critical` =
`level <= 0.1 && !charging`. Существующие вызовы обновить (один — в
`App.svelte:345`).

**Шаг Б-8. Третье состояние `data-saver='max'`.** Файл `app/src/App.svelte`:
`document.documentElement.dataset.saver = critical ? 'max' : on ? 'on' : 'off'`
(режим «on» руками остаётся просто «on»). Файл `app/src/app.css`: все
существующие селекторы `:root[data-saver='on']` дополнить парным
`:root[data-saver='max']` (через запятую). `Starfield.svelte`: условие
`saverOn()` — `dataset.saver === 'on' || dataset.saver === 'max'`.

**Шаг Б-9. Что гасит только 'max'.** `App.svelte`: полл бейджа — не ставить
таймер вовсе при 'max'; `DayScreen.svelte`: минутный тик `nowMs` — интервал
300 000 вместо 60 000 при 'max' (читать `dataset.saver` в колбэке —
достаточно, без реактивности). Хаптику не трогаем (событийная, копейки).

## C. Стратегия ступеней

**Ступень 0 — «Полная графика» (дефолт; saver=off, или auto при заряде >20%).**
Всё живое: блёстки 30 к/с, аврора-дрейф, матовое стекло (blur) шапки/таб-бара/
шторок, глоу выбранных элементов, переливы знаков, все пульсации. Для телефонов,
которые тянут — ничего не режем, это лицо приложения.

**Ступень 1 — «Экономия» (saver=on руками, или auto при ≤20% без зарядки).**
Уже реализована + дозакрывается шагами Б-1/Б-2. Исчезает всё ДВИЖУЩЕЕСЯ и
все ФИЛЬТРЫ: canvas-блёстки, аврора-дрейф, backdrop-blur (вместо него
непрозрачная тонированная подложка — темы сохраняют характер), все
drop-shadow/глоу колеса и карточек, переливы знаков (→ статичное золото),
infinite-пульсации и transitions становятся мгновенными, сетевой полл бейджа
пропускается (Б-4). Остаётся вся СТАТИЧНАЯ красота: градиентные фоны неба,
градиентные заголовки, text-shadow, цветовые кромки, глифы. Правило одной
строкой: «ступень 1 = ничего не движется и ничего не размывается, но всё
по-прежнему нарядное».

**Ступень 2 — «Аварийный минимум» (опционально; auto при ≤10% без зарядки).**
Всё из ступени 1 + гаснет фоновая активность: полл бейджа стоит совсем,
«живое сейчас» обновляется раз в 5 минут вместо минуты. Визуально от ступени 1
НЕ отличается — экономим уже не GPU, а таймеры и радио. Реализация — партия 3
(Б-7..Б-9), три мелких правки. Запускать только если владелица скажет, что
ступени 1 мало: прирост маленький, а состояние +1.

## D. App-only отличия (WebView/Android против сайта в десктоп-браузере)

1. **`env(safe-area-inset-*)` = 0 в Android WebView** (баг Chromium <140) —
   Capacitor 8 SystemBars инжектирует реальные значения как
   `--safe-area-inset-*`; в коде уже железное правило: только
   `var(--safe-top/--safe-bottom)`, не `env()` напрямую (`app.css:37-42`).
2. **`backdrop-filter` в WebView заметно дороже**, чем в десктопном Chrome:
   мобильный GPU слабее, а слой под шапкой перерисовывается на каждом кадре
   прокрутки. Именно поэтому blur снят с карточек ленты и остаётся только на
   немногих оверлеях — и целиком гаснет в saver. На десктопе тот же blur
   практически бесплатен: сайт «лёгкий», телефон — греется; профилировать
   ТОЛЬКО на устройстве (`chrome://inspect` → Performance monitor).
3. **Battery Status API** (`navigator.getBattery`) есть в Android
   WebView/Chromium → режим 'auto' в приложении работает. В Firefox и Safari
   API нет → на сайте 'auto' тихо равен 'off' (`lib/battery.ts:23-25`) —
   пользователю сайта экономию включать руками.
4. **Фоновое поведение таймеров/rAF различается, но итог одинаков — фон
   почти бесплатен.** Свёрнутое приложение: Android приостанавливает рендер
   WebView, rAF стоит (Starfield в фоне не жжёт), таймеры замирают до
   возврата. Фоновая вкладка сайта: Chrome стопит rAF и троттлит
   `setInterval` до ~1/мин. Отсюда правило: всю «свежесть» (OTA, бейдж)
   догонять на событии возврата — уже сделано через `appStateChange`
   (`App.svelte:224`), это чисто нативная ветка; у сайта аналога нет
   (допустимо: вкладку обновляют).
5. **Canvas в фоне**: WebView может сбрасывать GPU-ресурсы приостановленного
   канваса; Starfield каждый кадр рисует с нуля и переживает это без
   артефактов (состояние только в JS-массиве) — специально чинить нечего.
6. **Хаптика**: короткий `navigator.vibrate` многие прошивки игнорируют —
   в приложении уже нативный `@capacitor/haptics` с фолбэком ≥20 мс; на
   сайте остаётся web-вибрация где есть.
7. **`prefers-reduced-motion`** на Android завязан на «Убрать анимации» в
   спецвозможностях — включён у единиц; на десктопе встречается чаще. Поэтому
   saver — свой независимый рубильник и не полагается на reduced-motion
   (блок в `app.css:236-242` — отдельная, дублирующая страховка).
8. **Версии WebView разъезжаются с Chrome**: у части пользователей Android
   System WebView сильно старее (нет `color-mix`/`field-sizing` — фолбэки уже
   предусмотрены; `backdrop-filter` до WebView 76 отсутствует — стекло тихо
   становится прозрачным). На сайте десктопный Chrome всегда свежее — ещё одна
   причина не верить десктопным замерам.

## Что сознательно НЕ трогаем

- Архитектуру, движок расчётов (Swiss Eph WASM), авторские тексты/архетипы.
- Дефолтную графику: аврора, blur шапки, блёстки на сильных телефонах —
  осознанная цена «живого стекла», гасится только ступенями.
- Скраб колеса (WASM на кадр жеста) — уже rAF-дебаунс, это интерактивный пик,
  а не постоянка.
- Кэш дня (`lib/dayCache.ts`) — уже снимает повторные CPU-пики при листании.
