# Промпт для Fable — аудит энергопотребления интерфейса Astra

> Отдать этот текст Fable как ТЗ. Fable — архитектор: он не пишет код, он
> исследует интерфейс, выносит вердикт и пишет пошаговое ЗАДАНИЕ, которое потом
> выполнят дешёвые модели (Sonnet/Haiku) мелкими партиями. Один прогон покрывает
> и сайт, и приложение — приложение это тот же веб-бандл в обёртке Capacitor
> (Vite + Svelte 5 + TS), нативного кода почти нет. Анализируем ВЕБ, отдельным
> списком отмечаем немногие отличия WebView/Android.

---

## Роль и цель

Ты — архитектор производительности. Проанализируй интерфейс оффлайн-приложения
астролога **Astra** на энергопотребление (CPU/GPU/батарея/нагрев) на СЛАБОМ
Android-телефоне в WebView и напиши **пошаговое задание на оптимизацию**,
которое смогут безопасно выполнить более дешёвые модели.

**Главное ограничение — минимум потерь.** Владелица любит «живое стекло»: тёмная
«Аврора» со сполохами и блёстками, светлый «Рассвет». Красоту НЕ вырезать
насовсем. Всё тяжёлое гасить **ступенчато** и **условно** — через уже
существующий режим «Экономия аккумулятора» (`settings.batterySaver` →
`data-saver='on'` на `<html>`; значения `off | auto | on`, `auto` включается при
низком заряде через `lib/battery.ts`). Полная графика остаётся дефолтом для тех,
у кого телефон тянет.

## Контекст проекта (факты, не перепроверять с нуля)

- Стек: Vite + Svelte 5 (руны `$state/$derived/$effect`) + TypeScript + Capacitor.
  APK = тот же веб-бандл. Раздача sideload, оффлайн-первый, без сети в ядре.
- Расчёты неба: Swiss Ephemeris в WASM (`swisseph-wasm`, режим SWIEPH),
  детерминированы и уже кэшируются (`lib/dayCache.ts`). Это CPU-пики, не постоянка.
- Темы и «магия» живут в `app/src/app.css` (переменные тем, стекло, аврора-дрейф,
  блики). Режим экономии уже частично сделан — см. блок `:root[data-saver='on']`.

## Что заведомо ест ресурсы (проверь и уточни степень, не принимай на веру)

1. **`app/src/ui/Starfield.svelte`** — canvas со звёздами/блёстками, крутит рательный
   `requestAnimationFrame` постоянно. Кандидат №1 по расходу на слабом GPU. Уже
   умеет читать `data-saver` и останавливаться — проверь, что останавливается
   ВЕЗДЕ (в т.ч. при открытых шторках уже есть пауза) и что частота кадров/число
   частиц адекватны экрану.
2. **Аврора-дрейф** (`app.css`, `body::after`, `@keyframes aurora-drift`, 52s,
   `infinite alternate`) — постоянная композиция большого fixed-слоя.
3. **`backdrop-filter: blur(12px)`** на `.frost` и `section.sheet` — дорогой для
   WebView; уже снят с карточек ленты, оставлен на оверлеях. Проверь остаток.
4. **`filter: drop-shadow(...)` / glow** на выбранных линиях колеса, глифах,
   иконках знаков (`.glow-overlay`, `.selline`, `.signicon`, `.planet.sel`).
5. **Бесконечные микроанимации/пульсации** (любые `animation: ... infinite`).
6. **Перерисовки Svelte**: лишние `$derived`/`$effect`, пересчёт колеса при скрабе,
   массивы, которые мутируются на месте (`db.x.all()` возвращает ту же ссылку —
   в компонентах берут `.slice()`); ищи ре-рендеры, которые можно сузить.
7. **Reflow/repaint** при прокрутке лент и выезде шторок; тяжёлые тени/фильтры,
   висящие на каждом элементе списка.

## Что уже сделано (не ломать, дополнять)

- Блок `:root[data-saver='on']` в `app.css`: гасит аврора-дрейф, backdrop-blur
  шторок, glow-фильтры, делает анимации мгновенными; в saver-режиме под стекло
  подложена непрозрачная основа (иначе просвечивало).
- `Starfield.svelte` читает `data-saver` и стопорит rAF.
- `lib/battery.ts` (`watchLowBattery`) + `settings.batterySaver` (`off/auto/on`) +
  тумблер в `ui/DataPanel.svelte`.

## Что ты должен выдать

**A. Аудит-таблица consumer'ов.** Для каждого источника расхода: файл:строка,
тип нагрузки (постоянный rAF / композиция слоя / фильтр / перерисовка / CPU-пик),
оценка веса (высокий/средний/низкий), ЧЕМ жертвуем при отключении (визуальная
потеря) и рекомендация: (а) гасить только в `saver`, (б) гасить всегда, (в) сузить
без потери, (г) оставить.

**B. Пошаговое ЗАДАНИЕ для дешёвых моделей.** Разбей на МЕЛКИЕ независимые шаги
(урок проекта: крупные генерации теряются на лимитах — партии по 3–4 правки).
Каждый шаг:
- один файл или один связный кусок;
- точная правка (что было → что стало), с опорой на существующий
  `data-saver`-паттерн, без новых зависимостей;
- критерий приёмки (как проверить, что стало легче и красота не пропала при
  выключенном saver);
- пометка «сайт / приложение / оба» (по умолчанию оба — код общий).

**C. Стратегия ступеней.** Предложи 2–3 уровня: полная графика (дефолт) →
экономия (`saver`) → и, если нужно, аварийный минимум при критическом заряде.
Чёткое правило, ЧТО именно исчезает на каждой ступени.

**D. Отдельный короткий список app-only отличий** (WebView/Android): где нативная
обёртка ведёт себя иначе, чем сайт в десктоп-браузере (напр. `backdrop-filter`,
`env(safe-area)`, поведение canvas в фоне, троттлинг rAF при неактивной вкладке).
